# 측정 기록

봇을 고칠 때마다 여기에 남긴다. **어떤 조건에서 쟀는지**가 결과만큼 중요하다 —
이 파일이 없어서 같은 실수를 두 번 했다.

## 측정 규칙 (여기서 크게 데었다)

1. **표본이 부족한 결과를 신호로 읽지 말 것.**
   20세트의 95% 신뢰구간은 **±20%p** 다. 30% vs 50% 도 우연일 수 있다.
   최종 판단은 **60세트 이상**.
2. **탐색 예산을 낮춘 비교로 결론 내지 말 것.**
   `NODE_BUDGET` 1000 에서 45.8%(동률로 보임)였던 봇이 6000 에서 **13.3%** 였다.
   예산이 적으면 평가함수 차이가 드러나기 전에 탐색이 끝나 서로 같은 수를 두고,
   좌우 스왑 때문에 구조적으로 정확히 50% 가 나온다.
3. **좌우를 바꿔 잴 것.** 한쪽만 재면 진영 편향이 개선으로 둔갑한다.
   "득점 80:43 개선"이 스왑 후 100:95(무차이)로 드러난 적이 있다.
4. **약한 상대로 판단하지 말 것.** 13% 로 퇴보한 버전이 내장 AI 상대로는
   오히려 좋아 보였다(실점 1.00 → 0.42).
5. **승률 전에 `behavior.js` 를 볼 것.** 승률은 "나빠졌다"만 알려준다.
6. **CPU 부하에 주의.** 탐색은 `Date.now()` 로 시간을 재므로, 다른 작업이
   돌면 결과가 달라질 수 있다. 비교 중에는 백그라운드 작업을 띄우지 말 것.
   (`handicap.js` 는 시간 한도를 해제해 노드 한도만 물게 하므로 영향이 없다.)
7. **측정 중에 봇 파일을 다시 빌드하지 말 것.** 병렬 일꾼은 매 매치마다 파일을
   다시 읽는다. 도중에 빌드하면 중간부터 다른 봇을 재게 되고 결과에 안 드러난다.
8. ★ **대조 실험을 먼저 할 것.** 같은 파일끼리 붙여 **정확히 50%** 가 나오는지
   확인한다. 안 나오면 도구가 고장 난 것이고, 그 상태의 측정은 전부 무의미하다.

   ```sh
   node handicap.js --a X.js --b X.js --aBudget 6000 --bBudget 6000 --matches 20
   ```

   실제로 이걸로 하네스 버그를 잡았다(아래 "하네스 비결정론" 참고). 같은 봇끼리
   41.7% 가 나오는 걸 확인하지 않았다면 계속 숨어 있었을 것이다.

## 2026-08-31 세션

기준선은 `Leonyi_v1.js`(전탐색, NODE_BUDGET 6000, TIME_BUDGET_MS 45).

### 확정된 결과 (표본 충분)

| 변경 | 세트 | 결과 |
|---|---|---|
| 2수 지평선 평가만 (v2) | 60 | 51.7% — 차이 없음 |
| 위 + 롤아웃 정책 + 스펙 관측 + 수 섞기 (v4) | 80 | **30.0%** — 퇴보 |
| 수 섞기만 되돌림 (v5) | 60 | **13.3%** — 더 나쁨 |

→ 전부 되돌리고 `Leonyi_v1.js` 를 제출용으로 유지한다.

### 왜 안 됐는지 (계측으로 확인)

- **롤아웃의 95%가 지평선 전에 결말이 난다**(지평선 도달률 3~7%).
  그래서 지평선 평가를 아무리 정교하게 만들어도 잎의 5% 에만 영향을 준다.
  진짜 평가함수는 **롤아웃 정책** 자체다.
- **탐색은 노드 한도로 끊긴다**: 실제 사용 평균 5656/6000, 시간 중단 0회.
  따라서 `TIME_CHECK_MASK`(시계 확인 간격)는 평상시 손해가 없다.
- 탐색 평균 깊이 2.8~3.2.

### 결론이 안 난 것 (표본 부족, ±20%p)

- `TIME_CHECK_MASK` 255 vs 31 → 60~65% vs 40~55%. 노드 계수기와 모순되므로
  노이즈로 본다. 안전한 31 을 유지.
- `TIME_BUDGET_MS` 45/90/150 → 55%/50%/35%. 역시 결론 불가.

### 유지한 변경

- `TIME_CHECK_MASK: 31` — 시계를 32노드마다 본다. 256노드마다 보던 시절
  실측 최대 응답이 **362ms** 로 하드 타임아웃(360ms)을 넘겼다. 넘긴 응답은
  브라우저에서 폐기되고 그 틱은 무입력 = 실점이다. 노드 한도가 먼저 걸리므로
  평상시 비용은 0 이고, 노드 하나가 비정상적으로 비싸질 때만 작동한다.
  수정 후 최대 69ms.
- `decide()` 예외를 한 번만 콘솔에 출력 — 봇의 try/catch 가 예외를 삼켜서
  "가만히 있는 봇"과 "매 틱 터지는 봇"이 구분되지 않던 문제.

### 다시 하지 말 것

- **동점을 무작위로 깨기.** `candidateActions` 가 중립(0)을 먼저 넣는 순서
  자체가 설계다. 무작위로 깨면 봇이 결정을 못 하고 좌우로 떤다.
- 약한 상대(내장 AI·예제·LabA) 승률로 개선 판단하기.

## 병렬 평가와 핸디캡 대전 (2026-08-31 후반)

### 왜 만들었나 — 측정 상대가 고갈됐다

내장 AI·가이드 예제·전략 A·전략 C 를 전부 100% 로 이긴다. 자기 대전은 좌우
스왑 때문에 **정의상 50%** 가 나온다. 즉 개선을 잴 수단이 없었고, 그래서 계속
노이즈를 신호로 읽었다.

**해법: 상대에게 계산량을 더 준다.** 비대칭 대결이라 50% 함정이 사라지고,
"적은 계산으로 같은 결과를 내면 평가함수가 좋아진 것"이라는 해석이 가능하다.
`handicap.js`.

### 병렬화 — 표본 부족이 근본 원인이었다

30세트의 신뢰구간은 ±18%p 다. 이 세션의 실패는 대부분 여기서 왔다. 12코어에
나눠 돌려 **200세트를 153초**에 끝낸다(직렬이면 30분). 이제 ±7%p 로 판단 가능.
`parallel.js`, `worker.js`.

`handicap.js` 는 신뢰구간이 50%를 걸치면 **"결론 불가"로 표시하고 몇 판이 더
필요한지 알려준다.** 부족한 표본으로 결론 내는 실수를 도구가 막게 했다.

### 확정된 보정값

| 비교 | 200세트 결과 |
|---|---|
| 1000노드 vs 2000노드 | **2.5% ±2.2** — 예산이 실력을 압도적으로 좌우 |
| 1000 vs 1050 / 1150 / 1300 | 전부 **51.0%, 102승98패로 완전 동일** |

**탐색 깊이는 양자화되어 있다.** 반복 심화가 깊이 2를 완성하는 데 ~324노드,
깊이 3에 ~5832노드가 든다(분기 계수 약 18). 그래서 1000~1300 은 전부 "깊이
2까지"로 똑같이 동작한다. 예산을 조금 올리는 건 의미가 없고, **문턱을 넘겨야**
달라진다.

★ 출하 설정 `NODE_BUDGET: 6000` 은 깊이 3 문턱(~5832) **바로 위**에 걸쳐 있다.
대회 PC 가 조금만 느려 시간 한도가 먼저 걸리면 깊이 3을 못 채우고 실력이
급락할 수 있다. 확인이 필요하다.

### 철회한 주장

**"탐색을 깊이 할수록 약해진다"는 틀렸다.** 근거였던 `50노드 vs 6000노드 =
53.3%` 는 n=30, ±17.9%p 짜리 단일 측정이었고, 같은 표본의 다른 값들(100 이
50을 이김, 6000이 100을 이김)과 모순됐다. 200세트로 다시 재니 예산이 클수록
확실히 강하다. **부족한 표본으로 결론 내는 실수를 이 세션에서 네 번 했다.**

## 후보 가지치기 (2026-08-31)

### 동기와 실제 수치

계측으로 얻은 탐색의 실제 모습(예산 6000, 시간 해제):

```
분기 계수 = 평균 5.1 / 최대 12
깊이별 비용 = 1:10  2:63  3:346  4:1755  5:2590 노드
완성 횟수   = 400   400   395   395    78     <- 깊이 5는 20%만 도달
```

"분기를 줄이면 한 깊이 더 본다"는 기대로 세 규칙을 만들었다.

### 결과 — 셋 중 둘이 해로웠다 (각 100세트)

| 규칙 | 승률 | 판정 |
|---|---|---|
| `PRUNE_HIT` 공이 사거리 밖이면 파워히트 후보 제거 | 51.0% ±9.8 | 결론 불가 = 무해 |
| `PRUNE_JUMP` 공이 내 쪽으로 안 오면 점프 후보 제거 | 37.0% ±9.5 | **해로움** |
| `PRUNE_DIVE` 걸어서 닿으면 다이빙 후보 제거 | 15.0% ±7.0 | **매우 해로움** |

**"걸어서 닿는 거리면 다이빙은 손해"라는 직관이 완전히 틀렸다.** 다이빙은 이
봇의 핵심 수단이고, 후보에서 빼면 무너진다. 점프도 마찬가지다. 둘 다 판단 근거가
`expectedLandingPointX` 인데, 탐색 안에서는 그 값이 낡아 있어(skipLandingPrediction)
필요한 후보까지 지운다.

### 채택: PRUNE_HIT 만

| | 없음 | PRUNE_HIT |
|---|---|---|
| 분기 계수 | 5.1 | 4.2 |
| 깊이 4 비용 | 1587 | 570 |
| 깊이 5 도달률 | 30.5% | 78.9% |
| 승률 (100세트) | 기준 | 51.0% ±9.8 — 결론 불가 |
| **승률 (300세트)** | 기준 | **57.3% ±5.6 — 확정 개선** |

★ 100세트에서 "결론 불가"였던 것이 300세트에서 확정됐다. **도구가 성급한 결론을
막고, 표본을 늘리니 답이 나왔다.** 이 세션에서 다섯 번 실패한 지점이 바로 여기다.

같은 실력이 아니라 실제로 더 강하고, 덤으로 30% 적은 노드를 쓴다(느린 PC 보험).

### 철회 — "탐색 깊이가 실력을 지배한다"

`4000노드 vs 6000노드 = 15.8%` 를 근거로 "깊이가 전부"라고 했는데, PRUNE_HIT 이
**깊이 5 도달률을 30% → 79% 로 2.6배 올리고도 승률은 51%** 였다. 즉 깊이 4를
넘어서는 이득은 없다. 4000 대 6000 의 차이가 무엇에서 오는지는 아직 모른다.

이 세션에서 성급한 일반화를 다섯 번 했다. 패턴이 같다: 한두 개의 측정에서
그럴듯한 이야기를 만들고, 다음 측정이 그것을 뒤집는다. **측정은 가설을 확인하는
데 쓰고, 이야기를 만드는 데 쓰지 말 것.**

## 물리 발산 감지 안전장치 ([4c], 2026-08-31)

### 왜 만들었나

이 봇은 물리 엔진 복사본으로 미래를 계산해 수를 고른다. 그게 강점이지만,
**당일 새 스킬로 물리가 바뀌면 틀린 물리로 자신 있게 계획하게 된다.** 단순
휴리스틱 봇은 조금 나빠질 뿐이지만 이 봇은 크게 헛짚는다. 대회 최대 위험이었다.

미러가 실제 엔진과 프레임 단위로 일치한다는 건 검증돼 있으므로(53만 프레임,
불일치 0), **어긋남이 관측되면 그건 진짜로 규칙이 바뀐 것**이다.

### 동작

매 틱 "다음 틱의 공과 내 위치"를 적어 두고, 다음 틱에 실제와 대조한다.
계속 어긋나면 탐색을 끄고 단순 모드(엔진이 주는 expectedLandingPointX 만
믿고 몸으로 받아 넘기는 봇)로 내려간다. 미러를 고치면 자동 복귀한다.

판단은 두 가지다:
- **급성**: 최근 16틱 중 6회 이상 불일치 -> 물리가 크게 바뀐 경우
- **만성**: 누적 60회 이상 채점에서 불일치율 10% 이상 -> 조금씩 틀린 경우

### 오탐을 막는 것이 설계의 절반이었다

정상 물리에서 오탐이 나면 멀쩡한 봇이 단순 모드로 내려가 버린다. 오탐 원인을
하나씩 제거하며 27% -> 9% -> 8% -> **0%** 로 낮췄다:

| 오탐 원인 | 제외 방법 |
|---|---|
| 상대가 공을 침 | **관측된** 위치로 판정(예측된 상대 위치는 추정이라 빗나감). 예측 구간 양 끝에서 공이 두 플레이어 모두에게서 110px 이상 떨어져 있을 때만 채점 |
| 랠리 사이 구간 | 엔진이 물리를 안 돌린다. 공이 전혀 안 움직였으면 제외 |
| 득점 직후 슬로모션 | gameLoop 다섯 번에 물리 한 번. 스코어가 바뀌었으면 제외 |
| 랠리 시작 경계 | 한 틱에 물리가 2프레임만 도는 일이 있다(불일치가 "중력 한 번 덜 먹은" 모양). 랠리 50프레임 이후부터만 채점 |
| 공중에서의 내 y 예측 | y속도를 y좌표에서 역산하는데 정점 근처에서 상승/하강 분기를 틀린다. 세로는 지상일 때만 채점. **가로(x)는 공중에서도 채점** -- 안 그러면 이동속도 변경을 못 잡는다 |

### 검증 (엔진만 바꾸고 봇의 미러는 그대로 = 당일 상황과 동일)

| 시나리오 | 불일치율 | 단순모드 전환 | 첫 감지 |
|---|---|---|---|
| 정상 물리 | **0.0%** (389회) | 0/8 | — |
| 중력 +1 -> +2 | **100%** (917회) | **8/8** | tick 19 (약 2초) |
| 이동속도 6 -> 7 | 37.8% | 5/8 | tick 86 |

치명적인 경우(공 물리)는 2초 안에 확실히 잡고, 경미한 경우는 한 경기 안에 잡는다.

**이제 "물리가 바뀌면 망함"이 "안전하게 약해짐"으로 바뀌었다.** 그리고 콘솔에
무엇이 얼마나 어긋났는지 찍히므로, 당일 물리 미러를 어디부터 고칠지 단서가 된다.

## 하네스가 비결정론적이던 버그 (2026-08-31)

### 증상

내장 AI 끼리 **같은 시드**로 돌려도 결과가 갈렸다: 9:10 / 8:10 / 8:10.
같은 봇끼리 좌우 스왑하면 정확히 50% 가 나와야 하는데 41.7% 였다.

### 원인

`runMatch` 가 게임 객체를 **만든 뒤에** 난수를 시드했다. 그런데 생성자에서
`GameView` 가 구름 10개를 만들며 `rand()` 를 40회 뽑는다 -- 그 40회가 **직전
매치가 남긴 난수기**에서 나온다. 구름 위치가 매번 달라지고, 구름이 화면 밖으로
나갈 때마다 추가 난수를 소비하므로 물리용 난수 스트림이 어긋난다.

생성 후 시드는 브라우저 트레이스와 프레임 단위로 대조할 때 정렬을 맞추려고
일부러 넣었던 것이다. 그 용도로는 옳지만 평가에는 틀렸다.
지금은 `seedAfterConstruction` 옵션으로 분리했고 `compare.js` 만 그 모드를 쓴다.

### 고친 뒤

```
내장 AI 끼리 같은 시드 3회   5:10 / 5:10 / 5:10   (완전 동일)
같은 파일끼리 40세트          정확히 50.0% (20승 20패)
```

### 영향

이 버그는 이 세션의 모든 측정에 **잡음을 더했다**(평균은 치우치지 않는다).
핵심 결과를 고친 하네스로 재검증한 결과 결론은 유지됐다:

| | 버그 있을 때 | 고친 뒤 |
|---|---|---|
| 가지치기(v2) vs v1, 300세트 | 57.3% ±5.6 | **59.0% ±5.6** |
| 안전장치 vs 기준, 240/40세트 | 45.4% ±6.3 (결론 불가) | **정확히 50.0%** |

안전장치의 45.4% 는 **전부 이 버그였다.** 판단 자체는 2626회 비교에서 불일치 0
이었으므로 정확히 50% 가 맞는 값이다.

## 수비는 이미 포화 상태다 (coverage.js / stand.js)

**질문.** 지금까지 잰 것은 전부 **내 계보의 봇끼리**다(v1/v7/LabA/LabC + 내장
AI). 대회 상대는 남이 짠 봇이고, 무서운 건 "더 센 봇"이 아니라 **누구나 우연히
밟을 수 있는 구멍**이다. 그건 상대 없이도 잴 수 있다.

**방법(coverage.js).** 넘어오는 공을 격자로 만든다 — 네트를 넘는 높이 6가지 ×
수평속도 7가지 × 수직속도 9가지. 봇 없이 한 번 굴려 **우리 코트에 떨어지는
조합만** 남긴다(658개). 각 시나리오를 여러 봇에 똑같이 먹여서 돌려보내는지
본다. 도달 가능성 공식(오라클)을 쓰지 않는다 — 식이 틀리면 거짓 경보만 쌓인다.
대신 **다른 봇이 받으면 받을 수 있는 공**이라고 본다.

**검사기 자체의 함정 두 개를 먼저 고쳤다.**
- *봇 인스턴스 재사용.* 봇은 물리가 예상과 다르면 안전 모드로 내려가는 감시견을
  갖고 있다. 인스턴스를 돌려 쓰니 시나리오가 바뀔 때마다 공이 순간이동하는
  것을 "엔진이 바뀌었다"로 읽고 안전 모드에 빠졌다. **없는 구멍이 2개** 나왔다.
  시나리오마다 새로 컴파일해서 없어졌다.
- *리드타임 0.* 공을 네트에서 바로 시작하면 비행 5프레임짜리 공은 결정 기회가
  한 번뿐이다. 자유낙하를 거꾸로 풀어 최대 12프레임 앞에서 시작하게 했다.

| 봇 | 닿음 | 돌려보냄 |
|---|---|---|
| Leonyi_v10.js | 95.3% | 95.3% |
| Leonyi_v7.js | 95.3% | 95.3% |
| Leonyi_v1.js | 95.3% | 95.3% |
| 내장 AI | 91.0% | 87.7% |

**결론 1 — v10 에 고유 구멍은 없다.** 세 봇의 커버리지가 소수점까지 같다.

**결론 2 — 내장 AI 는 도달성의 기준이 될 수 없다.** AI 만 받는 공이 6개
있었는데, 전부 `vy=28`(최대 낙하각) · 낙하지점이 네트에서 50~70px · 비행
6프레임인 같은 모양이었다. 추적해 보니 AI 는 physics 안에서 **매 프레임 지연
없이** 움직이고, 제출 봇은 3프레임마다 결정 + 1프레임 지연이라 3프레임(18px)을
먼저 손해 본다. 그 18px 이 정확히 모자란 거리였다(4px 부족). **탐색을 아무리
잘 해도 그 공들은 못 받는다.**

**그래서 남은 조종 변수는 출발 위치뿐이다(stand.js).** 대기 위치를 왼쪽 코트
안에서 옮겨 가며 같은 329개 공을 받아 보게 했다.

| 대기 x | 전체 | 네트쪽(낙하>150) | 가운데 | 깊은쪽(<80) |
|---|---|---|---|---|
| 40 | 86.0% | 56.4% | 88.1% | 95.7% |
| 104 | 95.7% | 89.1% | 98.5% | 95.7% |
| **120** | **96.7%** | 94.5% | 98.5% | 95.7% |
| 136 | 96.7% | 96.4% | 97.8% | 95.7% |
| 184 | 93.9% | 94.5% | 94.8% | 92.8% |

**앞으로 나오는 것은 거의 공짜다.** 깊은 공 커버리지는 x=152 까지 95.7% 로
평평하다(깊은 공은 느려서 걸어 돌아갈 시간이 있다). 반면 네트쪽 짧은 공은
89% → 96% 로 오른다.

**그런데 실제 봇은 뒤에 서 있다.** 자기 대전 8세트에서 "공이 상대 코트에 있고
나에게 오지 않는" 프레임의 대기 x 를 모아 보니 평균 98, **최빈값 60~70**
(뒷벽이 32). 그 자리의 커버리지는 약 88% 로, 최적 대비 **8~9%p** 손해다.

→ `TUNE.STAND_FORWARD_BIAS` (대기 위치를 네트 쪽으로 당길 px) 를 넣었다.

## 대기 위치 하나가 탐색 개선 전부보다 컸다 (v10 → v12)

`STAND_FORWARD_BIAS` 를 핸디캡(후보 3000노드 vs 기준 6000노드)으로 훑었다.

| 값 | 승률 |
|---|---|
| 0 | 16.7% ± 7.7 |
| 20 | 4.4% ± 4.3 |
| **40** | **98.9% ± 2.2** |
| 60 | 88.9% ± 6.5 |

20 → 40 사이의 4.4% → 98.9% 는 매끄러운 최적점이 아니라 문턱이다. **핸디캡
측정은 이 세션에서 이미 한 번 방향까지 틀렸으므로**(v4 를 +25%p 라고 했는데
실제로는 −21%p) 전체 예산에서 다시 쟀다.

| 대전 | 승률 | 진영별 |
|---|---|---|
| v12 vs v10 | 89.2% ± 5.6 (120세트) | L 100% / R 78.3% |
| v12 vs v7 | 90.0% ± 5.9 (100세트) | L 80% / R 100% |
| v12 vs v1 | 80.0% ± 7.8 (100세트) | L 60% / R 100% |

v1 상대로는 v7 의 83.3% ±6.7 과 구간이 겹쳐 **차이 없음**이다. 즉 전진 수비의
이득은 **짧고 가파른 스매시를 쓰는 강한 상대에게 특화**되어 나타난다. 그게
[[승리 물리학]]이 말하는 최적 공격이라, 상대가 셀수록 이득이 커진다.

**대가도 있다.** 내장 AI 상대 40세트에서 실점이 세트당 0.15 → 0.95 로 늘었다
(승률은 양쪽 다 100%). 네트로 나오면 깊은 로브에 약해진다. 세트를 잃지는
않지만 알려진 약점이므로 상대의 공 깊이에 따라 조절하는 것을 다음에 시도한다.

**왜 이렇게 큰가.** 두 효과가 같은 방향으로 겹친다.
- 수비: 네트 바로 너머의 짧고 가파른 스매시를 덮는다. 그게 이 게임에서
  물리적으로 못 받는 공이다.
- 공격: 공을 네트 가까이에서 잡으면 **자기도 그 공을 칠 수 있다.**

자기 대전에서는 양쪽이 같은 최적 공격을 찾으므로, 그걸 더 잘 막는 쪽이 이긴다.

## 실점의 11% 는 "자리는 맞는데 떠 있어서" 놓친 공이었다

v12 의 이상행동을 v10 과 나란히 재니 하나만 크게 늘었다.

| | v10 | v12 |
|---|---|---|
| 내가 친 공이 내 코트에 낙하 | 2.4% (L 3.0 / R 1.8) | **11.1% (L 0.0 / R 22.4)** |

자기 대전이라 양쪽이 같은 봇인데 한쪽만 그렇다. 비율로는 알 수 없어 그 순간을
그대로 찍는 `owngoal.js` 를 만들었다. **20건 중 19건이 완전히 같은 모양이었다.**

```
공 (336,252)  내위치 (336,228) 상태=점프  입력 (0,0,0)
```

공의 x 와 내 x 가 **정확히 같다.** 낙하지점에 완벽히 서 있는데 놓친다.
서 있으면 y=244 라 바닥의 공(y=252)과 8px 차이지만, 점프 중에는 y 가 108~228
이라 **바닥 근처의 공에 몸이 닿지 않는다.**

프레임 단위로 추적하니(랠리 5, 55~86프레임) 이렇다.
- 55프레임: 공격을 위해 점프. **정당한 판단이었고 59프레임에 스매시에 성공한다.**
- 67프레임: 상대가 8프레임 만에 낮고 빠르게 되받는다. 낙하지점 336.
- 68~72프레임: 봇이 x=336 으로 정확히 이동한다.
- 73~86프레임: **자리는 맞는데 계속 공중이다**(y 111 → 228).
- 86프레임: 공이 (336,252) 바닥. 봇은 y=228.

즉 **점프 스매시는 성공해도 그 뒤 28프레임을 더 묶는다.** 확실히 끝내지 못하면
그 28프레임이 그대로 실점이 된다. 앞서 "헛점프 77% 는 손해가 작다"고 적었던
것은 틀렸다 — 점프 중에 x 이동이 자유로운 것만 보고 세로를 못 봤다.

**후보에서 빼는 것은 답이 아니다.** `PRUNE_JUMP=1` 은 이미 37% 로 확정 열세다.
점프 자체는 필요하다. 그래서 `TUNE.JUMP_PENALTY` 로 **확실히 더 좋을 때만
나오도록 값을 매기는** 쪽으로 간다(확실한 결말 ±1000 에는 매기지 않는다).

## ★ 거의 같은 봇끼리 붙이면 승률이 실력을 재지 않는다 (방법론 오류)

`hsweep.js` 는 같은 파일끼리 TUNE 만 바꿔 붙인다. 이 방식으로 `NODE_BUDGET`
을 훑었더니 이렇게 나왔다(기준은 6000, 100세트씩).

| NODE_BUDGET | 승률 |
|---|---|
| 400 | 84.0% ± 7.2 |
| 1000 | 37.0% ± 9.5 |
| 2000 | 44.0% ± 9.7 |
| 3000 | **100.0% ± 0.0** |
| 6000 | 50.0% ± 9.8 (대조군 — 완전히 같은 봇) |

**단조롭지 않다.** 400 에서 84%, 1000 에서 37%, 3000 에서 100%. 성능 곡선이
이런 모양일 수 없다. 대조군이 정확히 50.0% 라 하네스는 정상이다.

원인은 **결정론 + 거울 대전**이다. 같은 봇 같은 예산의 대조군은 전체 50% 이지만
진영별로는 **왼쪽 100% / 오른쪽 0%** 였다. 즉 한쪽이 전승한다. 두 봇이 거의
같으면 승패를 가르는 것은 실력이 아니라 "아주 작은 차이가 랠리를 어느 쪽으로
갈랐는가"이고, 그건 상수 값에 대해 매끄럽게 변하지 않는다. 나비효과다.

**그래서 자기 대전의 진영별 승률에 의미를 부여하면 안 된다.** 앞서 v10 의
"LEFT 18% / RIGHT 100%" 를 코트 비대칭이나 봇 버그로 해석했는데, 둘 다 아니고
이 현상이었다. 실제로 v12 는 상대가 달라지면 오른쪽이 더 강하기도 하다
(v7 상대 R 100%, v1 상대 R 100%).

**해법: `panel.js`.** 서로 다른 상대 여럿(v10 · v7 · v1 · LabA · LabC · 내장 AI)
에게 붙여 합계를 본다. 상대가 다르면 나비효과가 특정 값에 유리하게 몰릴 이유가
없다. 같은 `NODE_BUDGET` 을 이 방식으로 다시 재니 결과가 완전히 달라졌다
(각 값당 180세트).

| NODE_BUDGET | v10 | v7 | v1 | LabA | LabC | ai | 합계 |
|---|---|---|---|---|---|---|---|
| 400 | 90.0 | 90.0 | 93.3 | 100 | 100 | 100 | 95.6% ±3.0 |
| 1500 | 100 | 86.7 | 83.3 | 100 | 100 | 100 | 95.0% ±3.2 |
| 3000 | 100 | 100 | 83.3 | 100 | 100 | 100 | 97.2% ±2.4 |
| 6000 | 96.7 | 90.0 | 73.3 | 100 | 100 | 100 | 93.3% ±3.6 |

**네 값이 전부 구분 불가다.** 즉 탐색 깊이는 지금 승부를 가르는 요인이 아니다.
"400 이 6000 을 84% 로 이긴다"도, "깊을수록 좋다"도 둘 다 근거가 없었다.
그러면 예산은 실력이 아니라 **안전**을 기준으로 고르면 된다 -- 대회 PC 가
느릴 때 하드 타임아웃(360ms) 여유가 커지고, 15틱 연속 타임아웃 시 워커가
재시작되어 전역 상태가 전부 날아가는 최악의 경우를 막는다.

**어디까지 믿을 수 있나.** `STAND_FORWARD_BIAS=40` 은 이 함정을 통과한다 --
핸디캡 스윕(98.9%)만 믿은 것이 아니라 **서로 다른 세 상대**에게 전체 예산으로
확인했기 때문이다(v10 89.2%, v7 90.0%, v1 80.0%). 다만 v10 은 v12 와 상수
하나만 다르므로 그 89.2% 는 이 함정의 영향을 받을 수 있다. v7·v1 상대 결과가
근거다. panel.js 로 다시 확인한다.

## 점프에 값을 매기는 것은 해롭다 (진단은 맞았고 처방이 틀렸다)

자책골 해부로 "공중이라 낮은 공을 못 받는다"를 확인하고, 점프를 없애는 대신
값을 매기는 `JUMP_PENALTY` 를 넣어 `panel.js` 로 쟀다(상대 6종, 각 144세트).

| JUMP_PENALTY | v10 | v7 | v1 | LabA | LabC | ai | 합계 |
|---|---|---|---|---|---|---|---|
| **0** | 95.8 | 91.7 | 79.2 | 100 | 100 | 100 | **94.4% ±3.7** |
| 5 | 70.8 | 100 | 75.0 | 100 | 100 | 100 | 91.0% ±4.7 |
| 20 | 100 | 37.5 | 50.0 | 100 | 100 | 100 | 81.3% ±6.4 |
| 60 | 0.0 | 12.5 | 0.0 | 100 | 0.0 | 100 | 35.4% ±7.8 |

**올릴수록 단조롭게 나빠진다.** 진단(공중이면 못 받는다)은 사실이지만, 점프는
그 손해보다 버는 것이 훨씬 크다. `PRUNE_JUMP=1` 이 37% 였던 것과 같은 결론이다.
0 으로 둔다.

굳이 손대려면 "점프를 억제"가 아니라 **"늦게 점프"**(공이 가까워질 때까지
기다리기) 쪽이어야 한다 -- 문제는 점프 자체가 아니라 30프레임 전에 미리
결정해 버리는 것이기 때문이다. 아직 안 재 봤다.

## v14 — 최종 상수와 근거

`panel.js`(서로 다른 상대 6종에게 붙여 합계)로 네 가지를 훑은 결과.

| 실험 | 결론 |
|---|---|
| `NODE_BUDGET` 400 / 1500 / 3000 / 6000 | **전부 구분 불가**(93.3~97.2%). 탐색 깊이는 승부 요인이 아니다 |
| `JUMP_PENALTY` 0 / 5 / 20 / 60 | **단조 악화** 94.4 → 35.4%. 점프는 손해보다 버는 게 크다 |
| `STAND_ADAPT` 0 / 1 | **악화** 93.3 → 80.0%. 강한 상대에게만 무너진다 |
| `STAND_FORWARD_BIAS` 0~140 | **60 에서 정점** 95.6%. 0 은 81.7% |

세 실험이 같은 이야기를 한다 — **이 봇의 강함은 탐색이 아니라 "어디에 서 있는가"
에서 나온다.** 그래서 v14 는 상수 두 개만 바꿨다.

- `STAND_FORWARD_BIAS: 40 → 60`
- `NODE_BUDGET: 6000 → 3000` (강함 동일, 최대 decide 48.9 → 36.6ms)

**v14 vs v12 = 92.0% ±5.3** (100세트, LEFT 88.0% / RIGHT 96.0%).

음성 결과 둘도 값어치가 있다. 특히 `STAND_ADAPT` 는 **강한 상대에게만** 무너진다
(v10 46.7%, v7 60.0%인데 약한 상대는 100%). 강한 상대는 깊은 공도 섞어 쓰므로,
그걸 보고 물러나면 전진 수비의 이득을 스스로 반납한다. **"상대를 읽고 물러선다"는
접근 자체가 틀렸다.**

## 좌우 비대칭과 서브 — 사용자 관찰의 검증

사용자가 v14 자기 대전을 보고 "한쪽이 상대에게 강스매시 각을 너무 주기 좋게
넘긴다"고 지적했다. **현상은 맞았고, 일어나는 지점이 랠리 중이 아니라 서브였다.**

### 배제한 가설들 (`sides.js`, `coverage.js`, netedge 측정)

| 가설 | 결과 |
|---|---|
| 한쪽이 더 높은(때리기 쉬운) 공을 넘긴다 | ✗ 네트 통과 높이 L 142 / R 141 |
| 네트 경계의 파워히트 부호 규칙(`ball.x < 216`) | ✗ 양쪽 모두 발생 0.0%. 접촉 x 평균이 네트에서 112 / 105 로 대칭 |
| 수비 구조가 한쪽에 불리 | ✗ **거울 시나리오**에서 L 96.0% / R 94.5% — 오히려 왼쪽이 낫다 |
| 서브가 지는 자리 | **✓ 서브한 쪽 랠리 승률 L 0.0% / R 25.9%** |

첫 판(版) `sides.js` 는 프레임 단위로 세다가 "건드림 100.8%" 라는 불가능한 값을
냈다. **비율이 100% 를 넘으면 도구가 고장 난 것이다.** 소유(possession) 단위로
다시 짰다.

### 서브 추적

왼쪽 서브를 프레임 단위로 보면: 공이 x=56 에 수직 낙하 → 봇이 점프 →
15프레임에 파워히트 → 속도 (20, 0) **완전 수평** → 23프레임에 네트 통과(높이
164) → 24프레임에 상대가 점프해서 내려꽂는다. 받는 쪽에 20프레임의 준비 시간을
준다. 사용자가 본 "받기 좋은 각"이 이것이다.

### 그런데 더 나은 서브가 없다 (`serveTest.js`)

서브 구간만 손으로 강제해 랠리 승률을 비교했다(봇은 안 건드림).

| 정책 | 서브측 랠리 승률 |
|---|---|
| 기본(탐색이 결정) | 13.3% ±6.1 |
| 안 때리고 띄우기(네트 쪽으로 걸으며) | 11.7% ±5.7 |
| 안 때리고 띄우기(제자리) | 13.8% ±5.7 |

**전부 구분 불가.** 물리로도 설명된다 -- 서브는 x=56 에서 나가 상대 코트까지

→ 서브는 고칠 수 있는 약점이 아니라 게임의 구조다. 양쪽이 똑같이 당한다.
받는 쪽이 이기는 게임이고, 서브권은 랜덤이므로 기대값은 대칭이다.

**오른쪽**이 안정적으로 우세하다(왼쪽 승률 16.7% / 25.0%). 방향이 반대다.

확인해 볼 것.

# 낡은 낙하지점 — 평가함수를 오염시키던 상수 하나 (v16)

## 시작은 "서브가 무조건 점프 스매시다"는 지적이었다

사용자가 v14 의 서브를 지적했다. 추적해 보니 맞았고(f16 점프 → f22 파워히트 →
공 (20,0) 즉 높이 136 의 완전 수평), 공격 전반도 같은 편향이었다.

`attack.js` 로 재니 (v14 자기대전 4세트, 접촉 415회):

| | 봇이 실제로 고른 비율 | 놓친 자리의 정답 비율 |
|---|---|---|
| 위로 올려치기 (y=-1) | 9.6% | **39.1%** |
| 안 치고 이동 | 29.2% | 28.7% |
| 수평 (y=0) | **57.1%** | 18.4% |
| 내려꽂기 (y=+1) | 4.1% | 13.7% |

실제 득점률 53.7% / 최선 95.9% / **격차 42.2%p**.

★ **이 표를 처음 읽었을 때 라벨이 반대였다.** `attack.js` 가 `y===-1` 을
"스매시 아래"로 찍고 있었는데, physics.js:739 는
`ball.yVelocity = |v| * yDirection * 2` 이고 y 는 아래로 증가한다. 즉 **y=-1 이
위로**다. 반대로 읽으면 처방이 정반대로 나온다. 고쳤다.

## 원인 추적에서 두 번 빗나갔다

**가설 1 (기각).** "여유 식이 로브를 구조적으로 배제한다" — 페널티가 비행시간에
선형이라 27프레임을 넘는 공은 여유가 양수가 될 수 없다. 산술은 맞지만
**`ROLLOUT_FRAMES: 90` 이라 로브도 롤아웃 안에서 결말이 난다.** 여유는 지평선에
도달한 5% 에서만 쓰인다. 즉 진짜 평가함수는 롤아웃 정책이다.

**가설 2 (기각).** "시뮬 속 상대가 매 프레임 새로 결정해 3배 민첩하다" —
`advance()` 가 매 프레임 `guessOpponentInput` 을 부르는 것은 사실이고, 엔진은
`TICK_FRAMES`(3) 마다 한 번만 입력을 받는다. `SIM_TICK_CADENCE` 스위치로 고쳐
재니 패널에서 100% → 95% 로 **회귀**했다. (뒤에 밝혀지지만 이 회귀 판정 자체가
천장 효과였다. v14 직접 대전에서는 71% 다.)

## whynot.js — 추측을 멈추고 봇이 매긴 점수를 꺼냈다

두 번 빗나갔으므로 원인 후보를 가르는 도구를 만들었다. `TUNE.DIAG_ROOT` 로그를
가로채 각도별 최고점을 집계한다. 처방이 정반대이기 때문에 이걸 먼저 갈라야 한다:
(a) 탐색이 로브를 나쁘게 평가한다 → 평가를 고친다
(b) 점수는 같은데 안 고른다 → 동점 처리를 고친다

v14 1세트, 파워히트 각도가 선택지였던 111틱:

    탐색이 최고점을 준 각도   위로 45.9%  수평 47.7%  내려꽂기 6.3%
    수평 − 위로 점수차        73.0% 가 정확히 0

**(b) 였다.** 탐색은 로브를 거의 동등하게 평가하는데, `search()` 가 엄격한 `>`
로 최대를 고르므로 동점이면 `candidateActions` 의 순서가 이긴다. 그 순서가
`ORDER = [0,-1,1]` 이라 **수평이 항상 먼저**다. "중립(0) 먼저"라는 근거는 이동
축(x)에서는 타당하지만, 각도 축에서 y=0 은 중립이 아니라 그냥 평평한 강타다.
→ `SMASH_ANGLE_UP_FIRST` 스위치로 분리했다.

## 진짜 원인은 따로 있었다 — SIM_LANDING_REFRESH

미측정 플래그들을 **v14 직접 대전**으로 한꺼번에 쟀다(`ab.js`, 각 100세트):

|---|---|
| 대조 (전부 0 = v14) | 50.0% ±9.8 (50/100) |
| SIM_TICK_CADENCE=1 | 71.0% ±8.9 |

대조군이 정확히 50/100 이라 나비효과 구간이 아니다.

`SIM_LANDING_REFRESH: 0` 이면 `skipLandingPrediction` 때문에
`expectedLandingPointX` 가 갱신되지 않아, **타격으로 공의 방향이 뒤집힌 뒤에도

그 안의 선수들이 엉뚱한 곳으로 뛰고 있었으니, 모든 수의 값이 함께 틀어졌다.
비용은 "속도가 바뀐 프레임에만 재계산"이라 타격당 한 번뿐이다.

## 이번에 도구에서 배운 것

  +21%p 였다. 기준은 현 챔피언이어야 한다 → `ab.js`.
- **부하 중 타이밍은 비용이 아니다.** 병렬 11개가 도는 중 v16 이 mean 34ms /

  예산 400 에서도 v14 를 100% 이기고 max 13ms → `budget.js`.

## serveTest.js 는 지금까지 아무것도 재고 있지 않았다

앞 절("서브 — 더 나은 서브가 있는가")의 "다섯 정책 전부 구분 불가"는 **무효다.**

    if (s.rallyFrameCount < 3) touched = false;   // 새 랠리

두 겹으로 틀렸다. (1) 그 필드는 `s.meta.rallyFrameCount` 이므로
`s.rallyFrameCount` 는 `undefined` 이고 `undefined < 3` 은 false. (2) 경로를
고쳐도 안 된다 — 서브 구간이 열리는 시점의 실측값이 **3, 12, 14, 14, …** 라
`< 3` 이 한 번도 참이 되지 않는다. 그래서 `touched` 가 매치 첫 접촉에서 true 가
된 뒤 영영 리셋되지 않았고, **정책은 매치당 첫 서브 하나에만 걸렸다**
(실측: 서브 구간 29개 중 2개). 다섯 정책의 11.7~14.0% 산포는 정책 차이가 아니라
같은 봇을 다섯 번 잰 노이즈였다.

서브 구간 진입 전이로 리셋하도록 고쳤고 **29개 중 29개**를 확인했다.
→ 서브 정책은 아직 한 번도 제대로 측정된 적이 없다. 다시 잴 것.

# 서브 — 앞의 결론이 틀렸다 (v19)

## 왜 수평 서브가 그렇게 나쁜가

serveTrace 로 보면 탐색이 고르는 서브는 f16 점프 -> f22 에 높이 136 에서
파워히트 -> 공 (20, 0) 즉 **완전 수평**이다. 받는 쪽은 f24 에 이미 낙하지점에
자리를 잡고 기다렸다가 점프 스매시로 내려꽂는다. 우리 서브가 상대에게
공격하기 좋은 높이의 공을 배달하는 셈이다.

게다가 서버는 f16 에 떠서 f42 쯤까지 공중에 묶여 있는데, 상대의 반격은 f31 에
온다. 서브를 친 뒤 반격이 오는 내내 못 움직인다.

y=-1 로 올려치면 yVelocity = |낙하속도| x -1 x 2 로 공이 위로 뜬다. 상대에게
내려꽂을 각을 주지 않는다.

## 왜 탐색은 이걸 못 찾았나

서브 시점의 여유(margin)는 어떤 수를 둬도 음수다. 상대는 홈 포지션에 서 있고
비행시간이 길어 도달거리가 코트 반쪽을 덮는다. 그러면 모든 후보가 동점이 되고,
동점은 candidateActions 의 순서로 깨진다. 각도 순서가 [0,-1,1] 이라 **수평이
항상 이긴다.** whynot.js 가 보여준 "73% 의 틱에서 정확히 동점"이 여기서도
그대로 작동한다.

앞서 각도 순서를 뒤집는 처방은 랠리 전체에 적용해서 실패했다(30.0%). 서브는
상황이 좁고 정답이 확실하므로 **탐색에서 떼어내 손으로 정하는 편이 낫다.**
